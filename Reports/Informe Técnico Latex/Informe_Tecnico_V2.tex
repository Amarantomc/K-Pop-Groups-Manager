\chapter{Introducción}

Este documento describe la especificación técnica del \textbf{Sistema de Gestión de Agencias de K-Pop}. El sistema es una aplicación web diseñada para facilitar la administración de agencias de música K-Pop, permitiendo la gestión integral de grupos, artistas, aprendices, contratos, actividades y recursos relacionados.

\vspace{0.3cm}

El presente informe establece los lineamientos técnicos, requerimientos, arquitectura, seguridad e implementación del proyecto desarrollado por el Equipo \#1 durante el semestre académico 2025-2026.

\section{Propósito del Sistema}

\begin{itemize}
    \item Centralizar la información de agencias de K-Pop
    \item Administrar relaciones entre agencias, grupos y artistas
    \item Gestionar el proceso de evaluación de aprendices
    \item Mantener registro de contratos y actividades
    \item Generar reportes y estadísticas
\end{itemize}

\section{Alcance}

El sistema cubre 14 módulos principales que abarcan todas las operaciones de una agencia de K-Pop, desde la gestión de personal hasta la administración de activos de la empresa.

\chapter{Descripción del Problema}

Las agencias de K-Pop enfrentan varios desafíos en su operación diaria:

\section{Problemas Identificados}

\subsection{Desorganización de Datos}
\begin{itemize}
    \item Información dispersa entre múltiples sistemas
    \item Dificultad para acceder a datos históricos
    \item Inconsistencias en registros
\end{itemize}

\subsection{Gestión Compleja de Relaciones}
\begin{itemize}
    \item Múltiples relaciones entre entidades (agencias, grupos, artistas)
    \item Difícil rastrear cambios en status y evaluaciones
    \item Falta de visibilidad en el progreso de aprendices
\end{itemize}

\subsection{Falta de Automatización}
\begin{itemize}
    \item Procesos manuales propensos a errores
    \item Dificultad en generación de reportes
    \item Tiempo invertido en tareas administrativas
\end{itemize}

\subsection{Seguridad y Control de Acceso}
\begin{itemize}
    \item Información sensible sin protección adecuada
    \item Falta de auditoría de cambios
    \item Acceso sin restricciones por rol
\end{itemize}

\chapter{Solución Propuesta}

\section{Objetivo General}

Desarrollar una aplicación web moderna que centralice la gestión de agencias de K-Pop, proporcionando herramientas intuitivas y seguras para la administración de datos y procesos.

\section{Objetivos Específicos}

\begin{enumerate}
    \item Crear una base de datos relacional normalizada para almacenar información
    \item Desarrollar una API REST escalable para acceso a datos
    \item Implementar interfaz de usuario intuitiva para cada tipo de usuario
    \item Establecer controles de seguridad basados en roles
    \item Automatizar procesos críticos del negocio
\end{enumerate}

\chapter{Arquitectura del Sistema}

\section{Modelo de 3 Capas}

El sistema implementa una arquitectura de tres capas claramente separadas:

\subsection{Capa de Presentación}
\begin{itemize}
    \item Tecnología: React + TypeScript + Vite
    \item Componentes reutilizables
    \item Context API para estado global
    \item Interfaz responsiva
\end{itemize}

\subsection{Capa de Aplicación}
\begin{itemize}
    \item Tecnología: Node.js + Express + TypeScript
    \item Controladores HTTP
    \item DTOs (Data Transfer Objects)
    \item Lógica de negocio
    \item Inyección de dependencias
\end{itemize}

\subsection{Capa de Datos}
\begin{itemize}
    \item Tecnología: PostgreSQL + Prisma ORM
    \item Base de datos relacional
    \item Modelos y esquemas
    \item Migraciones versionadas
\end{itemize}

\section{Componentes Principales}

\subsection{Frontend (React)}
\begin{itemize}
    \item Framework: React 18+ con TypeScript
    \item Build Tool: Vite
    \item Estado: Context API
    \item Estructura: Organizada por feature
    \item Estilos: CSS modules
\end{itemize}

\subsection{Backend (Node.js + Express)}
\begin{itemize}
    \item Runtime: Node.js
    \item Framework: Express.js
    \item Lenguaje: TypeScript
    \item ORM: Prisma
    \item Patrón: Clean Architecture + Dependency Injection
\end{itemize}

\subsection{Base de Datos (PostgreSQL)}
\begin{itemize}
    \item Motor: PostgreSQL 12+
    \item ORM: Prisma
    \item Migraciones: Versionadas
    \item Entidades: 15+ modelos relacionales
\end{itemize}

\section{Patrones de Arquitectura}

\subsection{Clean Architecture}

La aplicación sigue el patrón Clean Architecture con capas claramente definidas:

\begin{verbatim}
Domain Layer (Entidades y Lógica de Negocio)
    ↓
Application Layer (Casos de Uso y DTOs)
    ↓
Infrastructure Layer (Repositorios y BD)
    ↓
Presentation Layer (Controladores)
\end{verbatim}

\subsection{Dependency Injection}

Se implementa un contenedor de inyección de dependencias que permite:
\begin{itemize}
    \item Registro de servicios centralizados
    \item Inyección automática en controladores
    \item Facilidad de testing y mocking
\end{itemize}

El Diagrama Entidad-Relación (MERX - Modelo Entidad-Relación eXtendido) representa la estructura lógica de la base de datos. Los diagramas en formato DrawIO pueden visualizarse en la aplicación Draw.io en línea o en VS Code con la extensión correspondiente.

\subsubsection{Relaciones Principales}

\begin{itemize}
\item Agencia \(\rightarrow\) Grupo (1:N) - Una agencia tiene múltiples grupos
\item Agencia \(\rightarrow\) Usuario (1:N) - Una agencia tiene múltiples usuarios gestores
\item Agencia \(\rightarrow\) Aprendiz (1:N) - Una agencia entrena múltiples aprendices
\item Grupo \(\rightarrow\) Artista (1:N) - Un grupo tiene múltiples artistas
\item Grupo \(\rightarrow\) Álbum (1:N) - Un grupo produce múltiples álbumes
\item Álbum \(\rightarrow\) Canción (1:N) - Un álbum contiene múltiples canciones
\item Grupo \(\rightarrow\) Premio (1:N) - Grupos pueden recibir múltiples premios
\item Actividad \(\rightarrow\) Ingreso (1:N) - Una actividad genera múltiples ingresos
\item Contrato \(\rightarrow\) Partes (M:N) - Contratos vinculan múltiples entidades
\end{itemize}

\chapter{Flujos de Negocio}

\section{Flujo 1: Login de Usuario}

El proceso de autenticación sigue estos pasos:

\begin{enumerate}
    \item Usuario ingresa email y contraseña
    \item Backend valida credenciales en BD
    \item Si son inválidas: Retornar error 401
    \item Si son válidas: Generar JWT token (exp: 24 horas)
    \item Generar refresh token (exp: 7 días)
    \item Retornar tokens y datos de usuario
\end{enumerate}

\section{Flujo 2: Crear Nuevo Grupo}

El proceso de creación de grupo:

\begin{enumerate}
    \item Usuario (MANAGER/ADMIN) ingresa datos del grupo
    \item Frontend valida datos localmente
    \item Si hay errores: Mostrar mensaje
    \item Si son válidos: POST /groups con datos
    \item Backend valida autorización (requiere MANAGER/ADMIN)
    \item Si no autorizado: Retornar error 403
    \item Backend valida datos
    \item Si falla: Retornar error 400
    \item Verificar nombre único
    \item Si existe: Retornar error 409
    \item Si es único: Crear grupo en BD
    \item Registrar en auditoría
    \item Retornar grupo creado (201)
\end{enumerate}

\section{Flujo 3: Evaluar Aprendiz}

El proceso de evaluación automáticamente determina estado:

\begin{enumerate}
    \item MANAGER accede a módulo de Evaluación
    \item Sistema obtiene lista de aprendices ACTIVE
    \item MANAGER selecciona aprendiz e ingresa evaluación
    \item Backend valida puntaje (0-100)
    \item Si es inválido: Retornar error
    \item Si es válido: Guardar evaluación
    \item Verificar promedio últimas 5 evaluaciones
    \item Si promedio >= 80: Estado = GRADUATED, crear Usuario ARTIST
    \item Si promedio < 40: Estado = SUSPENDED, notificar supervisor
    \item Si 40-79: Estado = ACTIVE, mantener
    \item Actualizar registro
\end{enumerate}

\section{Flujo 1: Autenticación de Usuario}

\subsection{Descripción}

Un usuario intenta acceder al sistema proporcionando credenciales (email y contraseña).

\subsection{Participantes}

\begin{itemize}
\item Usuario (Cliente Frontend)
\item Sistema (Servidor Backend)
\item Base de Datos
\end{itemize}

\subsection{Secuencia del Flujo}

\begin{enumerate}
\item \textbf{Inicio:} Usuario navega a \texttt{/login} y ve formulario
\item \textbf{Acción 1:} Usuario ingresa email y contraseña
\item \textbf{Validación 1:} Frontend valida formato de email localmente
    \begin{itemize}
    \item [X] Inválido $\rightarrow$ Mostrar error "Formato de email incorrecto"
    \item [OK] Válido $\rightarrow$ Continuar
    \end{itemize}
\item \textbf{Acción 2:} Usuario hace clic en botón Login
\item \textbf{Acción 3:} Frontend envía POST \texttt{/auth/login} con credenciales
\item \textbf{Validación 2:} Backend valida estructura de datos
    \begin{itemize}
    \item [X] Campos vacíos $\rightarrow$ Error 400 "Campos requeridos"
    \item [OK] Válido $\rightarrow$ Continuar
    \end{itemize}
\item \textbf{Validación 3:} Backend busca usuario en BD por email
    \begin{itemize}
    \item [X] No encontrado $\rightarrow$ Error 401 "Email o contraseña incorrectos"
    \item [OK] Encontrado $\rightarrow$ Continuar
    \end{itemize}
\item \textbf{Validación 4:} Backend valida contraseña (bcrypt compare)
    \begin{itemize}
    \item [X] No coincide $\rightarrow$ Error 401 "Email o contraseña incorrectos"
    \item [OK] Coincide $\rightarrow$ Continuar
    \end{itemize}
\item \textbf{Validación 5:} Backend verifica estado de usuario
    \begin{itemize}
    \item [X] Inactivo/Suspendido $\rightarrow$ Error 403 "Cuenta desactivada"
    \item [OK] Activo $\rightarrow$ Continuar
    \end{itemize}
\item \textbf{Acción 4:} Backend genera JWT (access token) válido por 24 horas
\item \textbf{Acción 5:} Backend genera refresh token válido por 7 días
\item \textbf{Acción 6:} Backend registra login en auditoría con timestamp e IP
\item \textbf{Retorno:} Backend retorna tokens al frontend (200 OK)
\item \textbf{Acción 7:} Frontend guarda tokens en localStorage/sessionStorage
\item \textbf{Acción 8:} Frontend redirige a dashboard según rol
\item \textbf{Fin:} Usuario autenticado en el sistema
\end{enumerate}

\section{Flujo 2: Evaluar Aprendiz (CRÍTICO)}

\subsection{Descripción}

Un manager registra una evaluación para un aprendiz. El sistema calcula automáticamente el promedio de últimas 5 evaluaciones y puede transicionar el estado del aprendiz automáticamente.

\subsection{Participantes}

\begin{itemize}
\item Manager/Director (acceso autorizado)
\item Aprendiz (sujeto de evaluación)
\item Sistema (cálculos automáticos)
\end{itemize}

\subsection{Secuencia del Flujo}

\begin{enumerate}
\item \textbf{Inicio:} Manager accede a "Gestión de Aprendices"
\item \textbf{Acción 1:} Manager busca/filtra aprendiz específico
\item \textbf{Acción 2:} Manager hace clic en botón "Evaluar"
\item \textbf{Validación 1:} Sistema verifica permisos de manager
    \begin{itemize}
    \item [X] Sin permisos $\rightarrow$ Error 403
    \item [OK] Con permisos $\rightarrow$ Continuar
    \end{itemize}
\item \textbf{Acción 3:} Se abre formulario de evaluación
\item \textbf{Acción 4:} Manager ingresa puntaje (0-100)
\item \textbf{Validación 2:} Sistema valida puntaje
    \begin{itemize}
    \item [X] Fuera de rango $\rightarrow$ Error "Puntaje debe estar entre 0 y 100"
    \item [OK] Válido $\rightarrow$ Continuar
    \end{itemize}
\item \textbf{Acción 5:} Manager opcionalmente agrega comentarios
\item \textbf{Acción 6:} Manager hace clic en "Guardar Evaluación"
\item \textbf{Acción 7:} Backend guarda evaluación en BD con timestamp
\item \textbf{Acción 8:} Backend recupera últimas 5 evaluaciones del aprendiz
\item \textbf{Acción 9:} Backend calcula promedio automáticamente
\item \textbf{Decisión 1:} ¿Promedio $\geq$ 80?
    \begin{itemize}
    \item \textbf{SÍ} → Ir a Ramificación A (Graduación)
    \item \textbf{NO} → Ir a Decisión 2
    \end{itemize}
\item \textbf{Decisión 2:} ¿Promedio $< 40$?
    \begin{itemize}
    \item \textbf{SÍ} → Ir a Ramificación B (Suspensión)
    \item \textbf{NO} → Ir a Acción 12
    \end{itemize}
\end{enumerate}

\subsubsection{Ramificación A: Graduación (Promedio $\geq$ 80)}

\begin{enumerate}
\item Cambiar estado de aprendiz a GRADUADO
\item Crear nuevo Usuario en BD con:
    \begin{itemize}
    \item email = apellido + número aleatorio@kpop.local
    \item rol = ARTIST
    \item nombre = nombre del aprendiz
    \item agencyId = misma agencia del aprendiz
    \end{itemize}
\item Generar contraseña temporal aleatoria
\item Enviar email al aprendiz con credenciales y enlace para cambiar contraseña
\item Registrar evento en auditoría: "APPRENTICE\_GRADUATED"
\item Notificar a director/admin de la graduación
\item Retornar confirmación al manager
\end{enumerate}

\subsubsection{Ramificación B: Suspensión (Promedio $< 40$)}

\begin{enumerate}
\item Cambiar estado de aprendiz a SUSPENDIDO
\item Generar reporte de bajo desempeño
\item Enviar notificación a supervisor asignado
\item Registrar evento en auditoría: "APPRENTICE\_SUSPENDED"
\item Crear tarea para revisión: "Revisar plan de recuperación para [Aprendiz]"
\item Retornar confirmación al manager
\end{enumerate}

\subsubsection{Continuación Normal (Promedio 40-79)}

\begin{enumerate}
\item Mantener estado como ACTIVO
\item Registrar evento en auditoría: "APPRENTICE\_EVALUATED"
\item Retornar confirmación al manager
\item \textbf{Fin:} Evaluación guardada y procesada
\end{enumerate}

\section{Flujo 3: Crear Nuevo Grupo}

\subsection{Descripción}

Un manager crea un nuevo grupo musical bajo la agencia, definiendo nombre, concepto y otros detalles.

\subsection{Validaciones Críticas}

\begin{itemize}
\item Nombre del grupo debe ser único en todo el sistema
\item Número de miembros debe estar entre 1 y 20
\item Fecha de debut no puede ser futura
\item Manager debe tener permisos (MANAGER/ADMIN/DIRECTOR)
\item Grupo debe pertenecer a una agencia válida
\end{itemize}

\subsection{Resultado}

Nuevo registro de grupo creado con estado INACTIVO hasta que tenga al menos un artista.

\section{Flujo 4: Registrar Ingreso}

\subsection{Descripción}

Se registra un ingreso (streaming, concierto, merchandising) que genera dinero para un artista o grupo. El sistema distribuye automáticamente según contratos.

\subsection{Cálculo de Distribución}

\begin{enumerate}
\item Buscar todos los contratos activos del grupo/artista
\item Para cada contrato activo, aplicar porcentaje de distribución
\item Registrar transacción de distribución en auditoría
\item Actualizar saldos pendientes de pago
\item Generar notificación de pago pendiente si aplica
\end{enumerate}

\subsection{Repository Pattern}

\begin{verbatim}
interface IRepository<T> {
  create(data: Partial<T>): Promise<T>
  findAll(): Promise<T[]>
  findById(id: number): Promise<T | null>
  update(id: number, data: Partial<T>): Promise<T>
  delete(id: number): Promise<boolean>
}

class UserRepository implements IRepository<User> {
  constructor(private prisma: PrismaClient) {}
  
  async findById(id: number): Promise<User | null> {
    return this.prisma.usuario.findUnique({
      where: { id }
    })
  }
}
\end{verbatim}
